# amnezia-mesh

Самохостова WireGuard-мережа з маскуванням трафіку AmneziaWG, MagicDNS та
профілями exit/mesh у стилі Tailscale — на одному VPS, за ~10 хвилин і без
залежностей, окрім Docker.

Уявіть «власний Tailscale», де кожен хоп належить вам: один невеликий сервер,
офіційний застосунок Amnezia на ваших пристроях і жодних серверів координації,
облікових записів чи сторонніх ретрансляторів.

## Можливості

- **CGNAT-мережа** (`100.64.0.0/24`, RFC 6598) — кожен пристрій отримує
  сталу IP; SSH/ping між пристроями йде через хаб, як `tailscale ssh`.
- **Маскування AmneziaWG 3.1** — рукостискання з junk-пакетами, підміна типів
  заголовків, ключ захисту заголовків, випадковий padding/trailer. Параметри
  **рандомізуються під час кожного розгортання**, тож DPI-відбитки в різних
  інсталяцій різні.
- **MagicDNS** — dnsmasq на хабі відповідає на `<пристрій>.<домен>` (наприклад,
  `laptop.awg`) і форвардить усе інше вашому апстрим-резолверу тунелем.
- **Профілі exit + mesh на пристрій** — `exit` гонить увесь трафік через VPS
  (обхід цензури); `mesh` маршрутизує лише CGNAT-підмережу, інтернет лишається
  напряму. Обидва генеруються для кожного пристрою.
- **Рідні профілі застосунку Amnezia** (`vpn://`) плюс звичайні `.conf` для
  будь-якого awg/wg-сумісного клієнта.
- **Незалежність від версій за дизайном** — образ AWG є зовнішньою, замінною
  залежністю; уся логіка живе на хості (див. «Дизайн»).
- **CLI, дружній до агентів** — кожна команда має вивід `--json`, перекриття
  через змінні середовища та неінтерактивний режим.

## Вимоги

- VPS із публічною IP, Docker з compose-плагіном і `python3`
  (>= 3.8, лише стандартна бібліотека — без `pip install`).
- Відкритий UDP-порт у фаєрволі VPS (рекомендовано 443/udp — він зливається з
  звичайним HTTPS/QUIC-трафіком і його найважче шейпити провайдерам).

## Встановлення з ШІ-агентом (Claude Code, Kimi Code, Cursor, …)

CLI має власний операторський скіл — компактний ранбук, що покриває
встановлення, протокол автоматизації, семантику рестартів і дерево рішень для
діагностики. Передайте його агенту — і весь сценарій стає розмовним:

```sh
# macOS cask: awg-mesh (CLI) та awg-mesh-tui. Linux: див. Releases.
brew tap alexpozdnyakof/tap
brew install --cask alexpozdnyakof/tap/awg-mesh
# або: git clone цього репозиторію

awg-mesh-tui install --ssh root@ВАШ_VPS --json
awg-mesh skill --install   # ~/.agents/skills/awg-mesh/SKILL.md
```

Далі просто попросіть, наприклад: *«налаштуй VPN на цьому VPS (IP 203.0.113.7),
додай мій ноутбук і телефон, потім запусти самоперевірки»*. Агент виконає
`awg-mesh init` / `peer add` / `doctor --json`, імпортує згенеровані профілі на
ваші пристрої та діагностуватиме зв'язність за деревом рішень скіла. `AGENTS.md`
у корені репозиторію робить ту саму орієнтацію для агентів, що працюють усередині
checkout.

## Швидкий старт (людина)

```sh
git clone https://github.com/<you>/amnezia-mesh && cd amnezia-mesh

./bin/awg-mesh init --host ВАША_IP_АБО_ДОМЕН --port 443
./bin/awg-mesh peer add laptop
# → друкує: config/peers/laptop-exit.vpn, laptop-mesh.vpn і варіанти .conf
# імпортуйте посилання .vpn у застосунок Amnezia на пристрої

./bin/awg-mesh peer add phone
./bin/awg-mesh doctor      # самоперевірка після встановлення
./bin/awg-mesh monitoring install   # опційно: cron-статистика + watchdog
```

На пристрої: застосунок Amnezia → імпорт посилання `vpn://` → підключитись.
Пристрої тепер бачать один одного за IP (`100.64.0.x`) і за ім'ям (`phone.awg`).

## Швидкий старт (агент / автоматизація)

```sh
export AWG_MESH_NONINTERACTIVE=1
./bin/awg-mesh --json init --host 198.51.100.10 --port 443
./bin/awg-mesh --json peer add laptop
./bin/awg-mesh --json doctor        # код виходу 0 = усі перевірки зелені
```

Вивід — один JSON-об'єкт на команду; при помилках код виходу ненульовий і
`{"ok": false, "error": "..."}`.

## Команди

| Команда | Опис |
|---|---|
| `awg-mesh init [--host H] [--port P] [--subnet CIDR] [--image IMG] [--domain D] [--rdp-reject]` | Генерація ключів + випадкового маскування, рендер конфігів, запуск контейнерів |
| `awg-mesh peer add <name> [--type exit\|mesh\|both]` | Новий пристрій: ключі, IP, профілі (застосування в реальному часі через `awg set` + SIGHUP dnsmasq — без рестарту; наявні піри не втрачають сесії) |
| `awg-mesh peer list` | Пристрої, IP, дати створення |
| `awg-mesh peer rename <name> <new-name> [pairs...]` | Перейменувати пристрій(ї) — приймає кілька пар старе/нове, щоб разом причесати згенеровані імена `peer-xxxx` після adopt (імена MagicDNS слідують; лише SIGHUP dnsmasq — без рестарту; валідація all-or-nothing, свопи підтримуються) |
| `awg-mesh peer rotate <name>` | Перевипустити ключі пристрою (та сама IP; хаб рестартує як при revoke — пристрій мусить повторно імпортувати профіль, старе посилання `vpn://` вмирає) |
| `awg-mesh peer revoke <name>` | Вилучити пристрій (контейнери awg + dns рестартує — вилучення пірів з userspace-демона через UAPI може безшумно заблокувати свіжі handshake; профілі видалено) |
| `awg-mesh doctor [--json]` | Docker, контейнери, порт прослуховування, ip_forward, MagicDNS, публікація портів |
| `awg-mesh dns add <name> <ipv4>` / `dns remove <name>` / `dns list` | Власні записи MagicDNS поверх `<name>.<domain>` (`nas.awg` → будь-яка IPv4) у `config/custom.hosts` — другий `--addn-hosts` для dnsmasq, перечитується через SIGHUP, без рестарту |
| `awg-mesh monitoring install\|uninstall` | Cron-статистика (`/var/log/amnezia-mesh-stats.log`) + watchdog |
| `awg-mesh adopt (--container C \| --config F --image IMG) --host H [--port P] [--dns1 D] [--dns2 D] [--rdp-reject]` | Мігрувати наявний сервер AmneziaWG під керування awg-mesh (див. нижче) |

## Віддалений режим (керування сервером із вашого Mac)

```sh
awg-mesh --server my-vps peer list --json   # або: export AWG_MESH_SSH=my-vps
```

Локальний CLI виконує `ssh my-vps 'cd ~ && awg-mesh <args>'` системним ssh-
клієнтом (аліаси й ключі з `~/.ssh/config`) і пропускає stdout/stderr/коди
виходу — локально логіка не дублюється. Після команди, що змінює стан
(`init`, `adopt`, `peer add|rename|revoke|rotate`), віддалений `config/peers/`
забирається назад через scp, тож профілі `.vpn` опиняються поруч із вашим
локальним checkout. `AWG_MESH_REMOTE_ROOT` задає корінь мережі на сервері
(за замовчуванням `~`). `skill` і `--version` завжди виконуються локально.

## Переведення наявного сервера під керування (adopt)

У вас уже працює AmneziaWG (контейнер або ручний деплой), і ви хочете
керування через `awg-mesh` — пірами, MagicDNS, doctor, моніторингом — **без
перевипуску жодного клієнтського профілю**.

```sh
./bin/awg-mesh adopt --container amnezia-awg --host ВАША_IP --port 443
# або з файлу конфігурації на хості:
./bin/awg-mesh adopt --config /root/awg0.conf --image amneziavpn/amneziawg-go:latest \
    --host ВАША_IP --port 443
```

Що переноситься **дослівно** (щоб клієнти нічого не помітили):

| | після adopt |
|---|---|
| приватний ключ сервера | той самий — клієнти бачать того ж сервера |
| профіль маскування (Jc/Jmin/Jmax/S/H, HeaderProtectionKey, таймінги) | той самий — DPI-відбиток не змінюється |
| публічні ключі та PSK пірів | ті самі |
| IP пірів | ті самі — беруться з `AllowedIPs` кожного піра |
| клієнтські профілі на пристроях | працюють далі, перевипуск не потрібен |

Що змінюється: контейнер перестворюється в compose-проєкті `amnezia-mesh`
(перейменовується на `amnezia-mesh-awg`, dnsmasq стає сайдкаром), і далі
деплоєм керує `awg-mesh`. Опції, які `awg0.conf` не може виразити — це прапорці:
`--dns1/--dns2` (апстрим-резолвери для форвардингу MagicDNS, за замовчуванням
1.1.1.1), `--rdp-reject` (правило reject для RDP UDP/3389), `--domain`
(за замовчуванням `awg`).

Покроково `adopt`:

1. читає `awg0.conf` — з контейнера (`--container`, образ визначається
   автоматично) або з файлу (`--config`, потрібен `--image`);
2. розбирає секції `[Interface]` + `[Peer]` у `config/server.env` +
   `config/peers.db` — натрапивши на невідомі ключі, **відмовляється** (з
   переліком проблемних ключів), а не мовчки їх втрачає;
3. рендерить `awg0.conf` / `dnsmasq.conf` / `start.sh` і запускає стек;
4. якщо `--container`: **зупиняє** старий контейнер (ніколи не вилучає) і
   запускає `doctor`; у разі невдачі відкочується автоматично — старий
   контейнер стартує назад, нічого не вилучено.

Правила безпеки:

- старий контейнер лише зупиняється й лишається на хості як план відкату:
  `docker stop amnezia-mesh-awg amnezia-mesh-dns && docker start <старий>`
- adopt переривається на невідомих ключах `[Interface]`, на `Address` сервера,
  що не є першим хостом підмережі, або на пірах без
  `PublicKey`/`PresharedKey`;
- імена пірів беруться з коментарів `# ім'я (added …)`; безіменні піри
  отримують згенероване ім'я `peer-xxxxxx`, колізії — суфікс `-2`.

## Дизайн: чому оновлення версій AmneziaWG не мають значення

1. **Образ AWG — звичайна залежність.** `docker-compose.yml` посилається на
   `amneziavpn/amneziawg-go` (перевизначається через `--image` або
   `AWG_MESH_IMAGE`). Нічого не форкнуто і не пропатчено; зміна тегу образу не
   потребує змін у проєкті.
2. **Уся логіка живе на хості.** Серверний конфіг, конфіг dnsmasq і entrypoint
   контейнера (iptables-бутстреп: forwarding, MASQUERADE, MSS clamp, опційний
   RDP-UDP reject) генеруються в `config/` і монтуються. Перестворення чи
   оновлення контейнера нічого не втрачає.
3. **Інтерфейс — стабільний UAPI.** Параметри `awg0.conf` (Jc/S/H,
   HeaderProtectionKey, таймінги) — частина протоколу AWG і не змінюються між
   релізами. Експериментальні параметри `I1`–`I5` (CPS) пробуються під час
   `init`; підтримка записується і сумісність зберігається в обох випадках.
4. **Профілі — рідний формат застосунку.** Профілі `vpn://` сумісні з тим, що
   експортує офіційний застосунок Amnezia, на рівні байтів
   (`base64url(uint32_be(len) + zlib(json, 9))`, компактні роздільники —
   перевірено байт-у-байт). Нові релізи застосунку далі їх імпортують.

## Структура

```
docker-compose.yml      контейнер awg + сайдкар dnsmasq (спільний netns)
bin/awg-mesh            точка входу CLI (тонкий шим, працює з checkout)
awg_mesh/               python-пакет: cli, envfile, peers, keygen, compose,
                        render, profile, doctor, adopt (лише stdlib)
scripts/                опційний моніторинг (stats, watchdog, cron)
tests/                  pytest-сьют: golden-файли рендера, peers db + flock,
                        roundtrip кодека profile
config/                 згенеровані секрети й стан — у gitignore, лишається на хості
```

## Як працює мережа (30 секунд)

WireGuard — це криптомаршрутизація: кожен пакет шифрується публічним ключем
піра, а `AllowedIPs` зіставляє IP призначення з піром. Телефон, що пінгує
`100.64.0.4`, шифрує ключем **хаба** — він ніколи не дізнається справжньої
адреси макбука. Хаб розшифровує, перешифровує ключем макбука і форвардить. Це
hub-and-spoke (маршрутизована мережа), а не P2P: працює за будь-яким NAT,
включно з мобільним carrier-grade NAT, де hole punching марний.
`PersistentKeepalive=25` з обох боків тримає NAT-пробиття відкритим, тому
пристрої взаємно досяжні.

## Нотатки з посилення захисту

- `config/` містить приватні ключі — він у gitignore, з правами 600 і ніколи
  не полишає сервер. Якщо перезбираєте VPS — бекапьте його в зашифрованому
  вигляді.
- Тримайте фаєрвол VPS у режимі default-deny; відкривайте лише SSH і обраний
  UDP-порт (443/udp найкраще зливається зі звичайним HTTPS/QUIC-трафіком).
- Маскування долає **відбитки** DPI, але не аналіз обсягу трафіку. Це не
  заміна Tor проти глобального пасивного спостерігача.
- `--rdp-reject` допомагає RDP крізь тунель (форсує миттєвий TCP-fallback
  UDP-каналу графіки). Увімкніть у `init`, якщо ганяєте RDP через мережу.

## Усунення несправностей

| Симптом | Перевірити |
|---|---|
| Пристрій не підключається | `awg-mesh doctor`; фаєрвол VPS пропускає UDP-порт |
| Довге «connecting», потім «connected», але інтернету нема | Майже завжди неправильний/застарілий профіль на пристрої: перевірте, який профіль активний у застосунку, і вилучіть старі/тестові |
| Домени не резолвляться на пристрої | перевірка magicdns у `doctor`; DNS у профілі пристрою мусить бути хабом (згенеровані профілі так і роблять) |
| Низька швидкість | MTU 1280 — навмисно (запас під padding); перевірте steal/CPU на малих тарифах VPS |
| `Protocol not supported` від `awg` CLI | відома вада amneziawg-tools на одиночних запитах ключів; використовуйте повний `awg show` — лише косметично |

## Тести

```sh
python3 -m venv .venv && .venv/bin/pip install pytest
.venv/bin/python -m pytest tests/ -q
```

Сьют не потребує ні Docker, ні мережі: рендер серверного конфіга звіряється
байт-у-байт з golden-файлами, зробленими початковою реалізацією; peers db
молотиться конкурентними письменниками, щоб довести серіалізацію `flock`; і
кодек `vpn://` проходить roundtrip-тести.
